1. 协作原则

你负责

  • 确认演示方向：目标故事线、优先级、是否进入下一阶段。
  • Android 编译：Android Studio、Gradle、JDK、签名、APK 生成。
  • 页面渲染调试：浏览器或设备屏幕上的最终观感、布局、交互检查。
  • 设备实测：APK 安装、人脸录入、刷脸、开门、logcat 或截图反馈。
  • 硬件信息：海康设备型号、系统版本、权限表现、485 接线与协议资料。

Codex 负责

  • 功能实现：原生 bridge、Web 状态机、mock 授权、错误处理。
  • 代码集成：AAR 依赖配置建议、Java 类、manifest 变更、JS 调用封装。
  • 问题修复：根据你提供的编译错误、运行日志、屏幕现象做最小必要修改。
  • 交接说明：每阶段说明改了什么、你需要怎么编译和怎么测。
重要调整：Codex 不承担 Android Studio 编译、APK 安装、页面渲染验收和实机操作本身；Codex 只根据你提供的结果迭代代码。这样职责边界更清楚，阶段推进也更稳。

3. 最终目标体验

  1. APK 启动后仍显示全屏电子门牌 kiosk，不破坏现有 10 个演示状态。
  2. 隐藏菜单增加 SDK 状态、人脸识别启动/停止、演示人脸录入、模拟通过/失败。
  3. 设备识别到人脸后，原生层把人员编号、姓名和事件码推给 Web。
  4. Web 层根据 mock 数据判断：人员是否登记、是否属于 302、培训是否有效、当前是否有已审批预约、实验室是否允许进入。
  5. 通过时 Web 调用 openDoor() 并显示成功 overlay；失败时不调用开门，显示明确失败原因。
  6. 后续在开门动作之后，按实机条件接入系统签名或 485/外部门禁协议。
演示身份策略：实机可以录入你的真实人脸，但 Web UI 一律展示虚构学生，例如“张一凡 / 材料研24”。真实生物特征只留在设备人员库中，不写入页面文案。

4. 阶段开发路线

阶段 0 · 基线冻结与可回退演示

目标：保住当前静态 APK

开发目标

  • 明确当前静态 demo 的可用状态，保证后续改坏时能回退。
  • 为无 SDK 的浏览器预览保留模拟入口。
  • 不改变现有门牌主视觉、隐藏菜单入口和息屏逻辑。

Codex 开发内容

  • 只做非侵入式准备：梳理入口、标注状态机、补充模拟事件函数。
  • 保留 DoorplateBridge.sleep/wake 原行为。
  • 如需加调试 UI，只放在右上角五连击隐藏菜单内。

参考依据

  • README.md 的 APK 专用入口说明。
  • www/index.html 中现有 SCENES、scan/success/fail 状态。
  • DoorplateBridgePlugin.java 的现有 bridge 写法。

验收标准

  • 你打开页面后，10 个状态仍可切换。
  • 无 Capacitor/无 SDK 时，模拟通过和模拟失败不报错。
  • 没有引入真实数据，没有破坏门牌视觉节奏。

你的动作用浏览器或设备检查页面渲染；确认当前版本可作为回退基线。

阶段 2 · 人脸认证事件桥接

目标：刷脸事件能进入 Web

开发目标

  • Web 可以启动/停止人脸认证。
  • 原生监听到人脸认证通过、失败、识别失败、真人检测失败。
  • 事件通过 Capacitor listener 推给 Web。

Codex 开发内容

  • 实现 startFaceVerify()，调用 VerifyType.verify。
  • 实现 stopFaceVerify()，关闭认证并移除监听。
  • 封装 faceVerifyEvent，包含 employeeNo/name/subEventType/raw。
  • Web 侧先只把事件映射到识别中、成功、失败三类状态。

参考依据

  • FaceIdentityActivity.java 的 openAccessVerify 与事件监听。
  • AccessControllerEventBean.java 的 employeeNoString 字段。
  • AcsEventMinor 中的人脸事件码。

验收标准

  • 你点击“启动识别”后，门牌显示识别中。
  • 实机刷脸后，Web 能收到事件并显示人员编号或失败原因。
  • 此阶段不调用 openDoor()。

你的动作实机刷脸，记录屏幕表现和 logcat；如果事件字段为空，把原始事件贴回给 Codex。

你的动作站在设备前录入人脸；确认设备采集条件、光线、距离和错误提示。

阶段 4 · Mock 预约核验

目标：识别出人后先判断能不能进

  • 成功 overlay 动态显示姓名、身份、预约时间。
  • 失败 overlay 动态显示“未登记 / 无权限 / 培训过期 / 无预约 / 实验室不可进入”。

验收标准

  • 你切换 mock 为有效预约时，页面显示允许进入。
  • 你切换 mock 为无预约或培训失效时，页面拒绝进入。
  • 此阶段仍不要求真实开门动作。

你的动作检查页面文案、失败原因、人物名称是否符合演示口径；确认没有真实个人信息。

阶段 5 · 显式开门联动

目标：预约通过后才调用开门

开发目标

Codex 开发内容

  • 实现 bridge 方法 openDoor()。
  • Web 侧在 authorizeFaceEvent() 通过后调用。
  • 保存最近一次开门结果到隐藏菜单调试区。

参考依据

  • AccessControlActivity.java 的 IHikManager.getAccessManager().openDoor()。
  • AcsEventMinor.MINOR_REMOTE_OPEN_DOOR 可作为事件参考。
  • 阶段 4 的授权结果。

验收标准

  • 有预约时，你能观察到门锁动作或 SDK 成功回调。
  • 无预约时，logcat 和页面都不能出现 openDoor() 成功调用。
  • 普通 APK 若权限不足，错误清楚显示，进入阶段 6 决策。

你的动作实机确认门锁是否动作；如失败，提供错误码、logcat 和是否需要系统签名的判断。

阶段 6 · 系统签名可选分支

你的动作负责签名构建、安装和权限验证；Codex 根据结果调整配置。

  • 发送测试帧有可解释反馈，或日志能定位节点/权限/波特率问题。

你的动作提供接线、节点、波特率、协议帧和设备反馈；Codex 负责把这些信息落到 bridge 实现中。

7. 风险与决策点

风险触发阶段表现处理
普通 APK 权限不足 阶段 1-5 SDK 初始化、采集或开门报权限错误。 你提供错误日志；Codex 进入阶段 6 配置系统签名分支。
事件不返回人员编号 阶段 2 只有通过/失败，没有 employeeNoString。 先读取 name/cardNo/pictureURL；必要时改为扫码 + 人脸二次核验。
VerifyType.verify 不触发识别 阶段 2 调用成功但设备无识别动作。 尝试配置 VerifyMode.FACE；仅为验证硬件链路时临时测试 verifyAndOpenDoor。
页面显示成功但开门失败 阶段 5 UI 欢迎进入，但门锁没动作。 开门回调必须覆盖 UI；成功 overlay 只在开门成功后展示。
485 节点不确定 阶段 7 发送无响应或权限错误。 你按设备排查节点和接线；Codex 只负责把确认后的节点和协议落代码。
